# 粗決議 01：Lingua 教材架構與生成流程

## 1. 產品定位

Lingua 是以 AI 協助建立、管理、使用外語教材的工具。產品重心是**生成一套有學習方向的課程**，而不是僅將任意文章轉成閱讀器內容。

- 一份**教材（Course）**由多個 **Units（單元）**組成。
- 教材可以服務於一般自我練習，也可以針對出國生活、特定考試、專業工作、學術研究或更特殊的任務。
- **單字驅動、實戰導向**：先決定情境與所需詞彙，再利用文章、對話、情境故事等材料學習如何實際使用。
- Lingua **不以文法課程為主要教學內容**；文法另行學習。材料仍應與指定程度相符，但具體難度控制方式未定。
- 既有 [Ultimate English Learner](https://github.com/XuBoKai1999/Ultimate_English_Learner) 可供參考，**不要求照搬其設計**。

## 2. GUI 的初步入口

希望操作簡單、以 GUI 管理已建立的教材，使用感接近資料夾瀏覽。

```text
Lingua
├── 進入教材
│   ├── 教材 A
│   │   ├── Unit 01
│   │   ├── Unit 02
│   │   └── ...
│   └── 教材 B
└── 創建新教材
```

「進入教材」用於開啟現有教材、Units 與相關學習材料。「創建新教材」透過引導流程及 Prompt 協助產生教材。

未來或許需要更高層的語言分類／管理，但目前**不預先增加層級**。上述是使用者概念模型，不等於已決定磁碟目錄、資料表或程式模組。

## 3. 四層教材生成規範（本次核心共識）

生成採**由上而下的四層流程**：

1. **教材總規範**：先決定語言、難度、方向／用途（出國、考試、專業任務等），以及其他必要限制。此層應處理整份教材的目標與取捨。
2. **Units 主題規劃**：依總規範決定各 Unit 的主題，例如看醫生、搭地鐵、大學生活、寫論文等。
3. **單一 Unit 的單字表**：按照教材總規範及 Unit 主題，產生該 Unit 的目標詞彙。
4. **詳細材料生成**：根據前述規範與單字表，產生多種形式的學習材料及所需音檔。具體材料設計尚未定案。

概念流程：

```text
語言／程度／用途／總規範
            ↓
      各 Units 主題
            ↓
     各 Unit 單字表
            ↓
  文章／對話／故事／其他材料
            ↓
         TTS 音檔
```

### 3.1 上層規範必須滲透至下層

**關鍵不是單純將上一階段的輸出交給下一階段，而是保留所有仍然有效的上層規範。**

例如「B1 英文、出國生活」與「C1 英文、醫學專業交流」即使都有「看醫生」Unit，其詞彙選取與材料語氣、難度及情境也應不同。第四層不能只看到單字表而遺失教材總目標。

生成各階段 Prompt 時，應將**相關上層規範 + 當前層資訊**一起提供給 AI，以維持縱向一致性。

### 3.2 JSON 與 Prompt 的角色

- 初步構想是使用若干固定的 **JSON 規範／結果**控制不同生成階段。
- 上層的有效規範最終應進入下層的 **Prompt**。
- 初期可採**使用者複製 Prompt、與 AI 對話、貼回生成結果**的工作流。
- 後期再考慮以 API 自動執行相同工作流。
- **JSON 欄位、檔案拆分、Prompt 組合方式均未定稿**；目前不制定正式 schema，也不要求額外存一份合併後的 JSON。

## 4. Unit 與材料的概念

一個 Unit 以主題為範圍，核心為**單字表**，再由詞彙生成可以實際接觸、理解與使用語言的材料。

可能的材料形式：

- 文章
- 雙人或多人對話
- 情境故事
- 其他符合 Unit 目標的內容（待討論）

同一 Unit **可以有多份材料**，不要求所有 Units 都具有相同的材料組合。教材生成階段會涉及 TTS，讓材料可聆聽。

單字表的「單字」是否包含片語、固定搭配（lexical chunks）、各材料的覆蓋率與重複規則，都曾被提出，但**尚未形成正式決議**。目標不是為了硬塞指定詞彙而產生不自然的文章。

## 5. 學習體驗與能力範圍

目前的需求描述：

- **聽與說**：使用者已明確指定為每個 Unit 的必要方向。
- **TTS／聆聽**：屬教材生成及使用時的重要基礎能力。
- **閱讀**：最初已提出第一版至少能聽、能讀，並可參考既有專案的閱讀與播放介面。
- **讀寫練習／更深入互動**：可視 API 進度後續開放，也可能透過引導 Prompt 直接移至 GPT 對話完成。

**待釐清的界線**：上述「讀」作為文字材料的基本閱讀功能，與「閱讀理解練習」並不相同；先前同時出現「初期至少聽讀」與「讀寫後期開放」兩種描述。此處不擅自裁定第一版必須完成哪些互動練習。

口說練習具體採跟讀、角色扮演、自由表達、外部 GPT 語音對話或程式內語音互動，尚未決定；**TTS 本身不等於已完成口說練習設計**。

## 6. 曾討論但尚未定案的設計建議

以下是討論中提出的可能方案，**不是已承諾的需求**：

- 讓使用者逐層檢查／修改 Unit 規劃、單字表與材料，而非一次全部生成。
- 讓同一份詞彙表衍生多篇不同情境的材料，並容許局部重新生成。
- 追蹤跨 Unit 的詞彙重複，以區分新詞、自然複習與意外重複。
- 將語言、程度、用途視為不同性質的限制（硬性條件、難度指引、選材優先順序），而非全部一樣強制。
- 上層規範修改時提示下游內容可能失效，而非逕自覆寫。
- 將文字與 JSON 作為可保存的來源、音檔視為可再生成的衍生物（參考既有專案，但尚未針對 Lingua 定案）。

## 7. 待後續討論

1. 一個 Unit 的實際學習流程：使用者進入之後先看什麼、做什麼？
2. 材料有哪些形式、各自的生成規格與最低品質要求？
3. 單字表如何決定詞彙數量、範圍、片語與跨 Unit 重複？
4. 聽、說、讀、寫各自的最小可行功能；初期與 API 階段如何切分？
5. TTS 的生成、播放、角色聲音及音訊與文字的同步方式。
6. 四層 JSON 的 schema、驗證、版本與 Prompt 組合機制。
7. 如何局部重生、人工審查，以及處理上層修改對下層的影響。
8. 多語言教材與 GUI 更高層管理是否必要。
